===========================================
ANDROID APP LANGUAGE — 4 OPTIONS
===========================================
Context: The final deliverable is a private, single-APK Android companion
app ("Macro Monitor") for monitoring/controlling Natro Macro instances on
a Windows PC. A polished HTML prototype already exists and should be the
visual design reference. It will talk to a Windows-side bridge service
over a private network (Tailscale).

Build environment (host PC = Windows, user "67"):
  - Java 1.8.0_401 installed (TOO OLD — modern Android builds need JDK 17+)
  - NO Android SDK, NO adb, NO Android Studio, ANDROID_HOME empty
  - Python 3.14.4 and Node v24.19.0 available (relevant for the bridge, not the app)
  - Plan: install Temurin JDK 21 + Android command-line tools, build with gradlew
    (no Studio required). Toolchain install ~600 MB.

-------------------------------------------
OPTION 1 — Kotlin + Jetpack Compose        [RECOMMENDED]
-------------------------------------------
  What   : Native Android app, declarative Kotlin UI.
  Pros   : The standard/first-class Android stack. Best long-term
           maintainability, full native API access (notifications,
           background sync, WebView), modern look that can match the
           prototype closely.
  Cons   : Any rework of the prototype design must be hand-built in
           Compose (no direct HTML reuse).
  Effort : Moderate. Best choice for a real, long-lived app.

-------------------------------------------
OPTION 2 — Kotlin + XML views
-------------------------------------------
  What   : Native Kotlin, classic XML layout files instead of Compose.
  Pros   : Battle-tested, enormous amount of documentation/tutorials.
  Cons   : More boilerplate (findViewById/adapter code), dated look
           unless carefully styled, slower to iterate.
  Effort : Moderate-to-high for this kind of dashboard UI.

-------------------------------------------
OPTION 3 — Capacitor / web wrapper
-------------------------------------------
  What   : Wrap the existing HTML prototype in an Android WebView shell;
           the JS app becomes the actual UI.
  Pros   : Fastest to ship — reuses ~90% of the prototype as-is. Still
           needs the same Android SDK to produce the APK.
  Cons   : Less native feel/performance; JS-to-device bridge limits for
           notifications/background work; HTML app must be adapted for
           real data (currently demo/fake data only).
  Effort : Low-to-moderate. Best as a quick fallback.

-------------------------------------------
OPTION 4 — Flutter (Dart)
-------------------------------------------
  What   : Cross-platform framework, custom-rendered UI.
  Pros   : Very polished UI possible, hot-reload dev speed.
  Cons   : ~2 GB extra toolchain for a one-platform need; Dart dev cost;
           still needs the same Android SDK to build.
  Effort : Moderate. Hard to justify when Android is the only target.

===========================================
RECOMMENDATION: OPTION 1 (Kotlin + Jetpack Compose).
Single-platform app -> use the platform's own native stack.
The HTML prototype stays the design source of truth; no HTML is shipped.
===========================================
